# AM и FM в NEST 3.10

## Двухпороговые модели с физическим кальцием

`bash astrocyte_lab/scripts/nest_physical_compare.sh` из корня репозитория по очереди собирает и измеряет улучшенные AM/FM модели: `identity` в (C,h) и `power` в (C,q), q=h^gamma. Для них C — прямая переменная, а не нормированная координата `C/0.5-1`. По умолчанию шаги 0.1 и 1.0 мс; для каждого варианта и шага — изолированный астроцитарный benchmark с SIC и без SIC, одно- и 16-поточный, и сеть 10 возбуждающих нейронов со 90 астроцитами (16 потоков). 64 узла на обоих потоковых сценариях позволяют сравнивать время при одинаковой нагрузке. Задайте `NEST_RESOLUTIONS_MS='0.1'`, `RUN_NETWORK=0`, `NEST_DURATION_S`, `NEST_VALIDATION_S`, `NEST_REPEATS`, `NEST_SINGLE_NODES`, `NEST_MULTI_NODES`, `NEST_THREADS`, `NETWORK_DURATION_S`, `NETWORK_THREADS`, `NETWORK_REPEATS` по необходимости. Каталог `RUN_DIR` и каждый запуск печатаются в консоль; результаты разделены по координатам и шагам.

В NEST-поле `h_IP3R` у `power` хранится именно q, а не исходная h LR. В начальном покое q берётся из равновесия модели; при общей LR инициализации преобразуется в h^gamma. Сравнение реализации PWA с независимым интегратором проверяет C, q и IP3, в том числе физический диапазон q на записанной траектории. В сравнении с LR для `power` метрика ошибки h намеренно отсутствует: q и h не равны; сравниваются C, IP3 и SIC. Для `identity` скрытая переменная численно h. Время `nest.Run` измеряется отдельно от построения сети и записи, LR и PWA используют одинаковые топологию, число узлов и входы, но свои равновесия. Это время конкретной схемы, а не оценка всех сетей. Шаги и запись не гарантируют обнаружения кратных пересечений за шаг; успешная валидация не доказывает точности по всем входам. Дополнительная модель со свободной q здесь не поддерживается.

Этот эксперимент собирает два экспериментальных NEST-узла: `astrocyte_am_pwa` и `astrocyte_fm_pwa`. За основу интерфейса взят астроцит `astrocyte_lr_1994` из NEST 3.10; исходные файлы и лицензия находятся в `module/upstream` и `module/COPYING`. Коэффициенты двух выбранных кандидатов встраиваются при сборке, SHA256 записывается в манифест. Это отдельный модуль, штатная LR остаётся доступна.

В модели задана кусочно-аффинная динамика в `(z,h)`, `z=Phi(C)`, пороги по z и экспоненциальное затухание IP3; входящие `SpikeEvent` дают такой же скачок IP3, как в LR. Состояние между шагами хранится в `(z,h,IP3)`; физический C вычисляется для записи и при формировании ненулевого SIC, который отправляется штатным способом. Время модели в секундах, интерфейс NEST в миллисекундах. Внутри области используется точный аффинный поток для экспоненциального IP3; матрицы кэшируются. При обнаружении пересечения порога время уточняется. Обращение Phi выполняется методом Ньютона с защитной бисекцией. Проверка пересечений использует концы шага: несколько пересечений внутри одного шага могут остаться незамеченными.

`CurrentEvent` с ненулевым током не поддерживается. Биофизические параметры поля фиксированы под выбранный JSON и не перенастраиваются через NEST: изменение `Km_SERCA` и параметров каналов для PWA отклоняется; для другого K нужна новая подгонка и пересборка. Зато `IP3_0`, `IP3`, `tau_IP3`, `delta_IP3`, `Ca_astro`, `h_IP3R`, `SIC_th` и `SIC_scale` настраиваются. В сравнениях LR использует `Km_SERCA=0.1` для AM и `0.05` для FM.

## Сборка и запуск

Активируйте окружение с NEST 3.10 и из этой папки выполните:

```bash
bash run_benchmarks.sh
```

По умолчанию берутся файлы `../am_two_thresholds/fits/mixed_power_fixed/candidate.json` и `../fm_four_zone_fit/candidate.json`. Для выбора других исходных JSON задайте `AM_CANDIDATE` и `FM_CANDIDATE` до сборки. `build_module.sh` читает эти файлы и создаёт отдельный модуль; файлы кандидатов не изменяются. При изменении кандидата требуется пересборка, а benchmark проверяет хеши.

Если в активном окружении не найдены CMake или заголовки Boost/libltdl, `setup_build_tools.sh` создаёт отдельную служебную Python-venv в `module/deps/tools`, скачивает CMake и закреплённые версии заголовков в `module/deps`. Системные пакеты не изменяются. Нужны интернет, `g++`, `nm`, Python 3.12 с venv/pip и NEST с заголовками. Сборщик распознаёт повреждённые пути `nest-config` из pip wheel и C++ ABI загруженного `nestkernel_api.so`. Можно задать `NEST_CONFIG`, `NEST_INCLUDE_DIR`, `BOOST_INCLUDE_DIR`, `NEST_CXX`, `NEST_GLIBCXX_ABI` и `BUILD_JOBS`.

Пакетный запуск проводит один сценарий с тремя фиксированными спайками и экспоненциальным IP3, с SIC-соединением и без него; каждый AM/FM сравнивается с LR при одинаковых входах и количестве узлов. Сначала 16 астроцитов на одном потоке, затем 64 на 16 потоках. После отдельного прогрева каждый вариант повторяется 3 раза в чередующемся порядке. Время — wall time `nest.Run` после `nest.Prepare`; подготовка и завершение NEST сохраняются отдельно, сборка и создание сети исключены; `speedup = median(LR) / median(PWA)`. Другие настройки: `NEST_DURATION_S`, `NEST_VALIDATION_S`, `NEST_RESOLUTION_MS`, `NEST_SINGLE_NODES`, `NEST_MULTI_NODES`, `NEST_THREADS`, `NEST_REPEATS`, `NEST_PROTOCOL`. По умолчанию длительность 20 с, шаг 0.1 мс. Шаг и сценарий влияют на скорость и точность.

Перед замерами `verify_nest_state.py` сравнивает одну длинную и две последовательные симуляции и проверяет старт на порогах с движением в обе стороны. Затем численная траектория каждой PWA сравнивается с независимым SciPy DOP853 на том же сценарии и тех же временах доставки спайков. Если проверка не пройдена, benchmark прекращается. Это сравнение проверяет реализацию PWA, а не точность PWA относительно LR. Отдельно сохраняются RMSE и максимальные расхождения C, h, IP3 и полученного нейроном SIC между PWA и встроенной LR. LR применяет собственные фиксированные допуски GSL; результаты сравнения ограничены выбранным сценарием.

Выход — уникальный `results/nest_<UTC>_<pid>/`: `one_thread.json`, `multi_thread.json`, журналы, соответствующие NPZ с трассами и PNG/PDF сравнения. Численный поиск и траектории не доказывают отсутствие дополнительных пересечений или циклов.

## Проверка ядра вне NEST

`validate_latent_flow.py` проверяет отдельный C++ поток в преобразованных координатах против DOP853 и не является NEST benchmark.

## Протокол из ветки work

В `work-pulse` по умолчанию LR стартует из своего равновесия, а PWA — из устойчивого физического равновесия своей модели при том же базовом IP3. Если их несколько, выбирается ближайшее по C к равновесию LR. Чтобы воспроизвести прежний запуск с одинаковым начальным состоянием LR и PWA, задайте `PWA_INIT_MODE=lr`. Начальные состояния и режим сохраняются в JSON; сравнения отвечают на разные вопросы. Исправление относится к начальному состоянию NEST, а не к решателю складки при подборе FM.

Для сопоставления с `results/nest_benchmark/resolution_sweep.json` из `work` можно использовать тот же вход `pulse_tau20`: покой LR, IP3=0.2 для AM или 0.45 для FM, один скачок IP3=0.7 на 20-й секунде, tau=20 с, задержка соединения 10 мс, шаг 0.1 мс. Длительность обеих стадий должна быть больше 20 с. Пример:

```bash
NEST_PROTOCOL=work-pulse NEST_DURATION_S=60 NEST_VALIDATION_S=30 \
  NEST_SINGLE_NODES=64 NEST_MULTI_NODES=64 NEST_THREADS=16 bash run_benchmarks.sh
```

Однопоточная часть использует 64 астроцита, как опубликованный sweep из `work`, с прогревом и тремя повторами. В `work` были другие сами модели и подстановки координат, поэтому этот прогон сопоставляет условия, но не является повтором той же модели. Для сравнения только `nest.Run` берите `speedups`; время `Prepare` и `Cleanup` записано отдельно.

## Профилирование

`bash profile_server.sh` проводит отдельные прогоны с обычной сборкой и со счётчиками в C++ PWA. По умолчанию используются собственные равновесия, 64 узла, один и 16 потоков, шаг 0,1 мс, 30 с модельного времени и три повтора. `NEST_DURATION_S`, `NEST_VALIDATION_S`, `NEST_SINGLE_NODES`, `NEST_MULTI_NODES`, `NEST_THREADS`, `NEST_REPEATS`, `NEST_RESOLUTION_MS`, `AM_CANDIDATE`, `FM_CANDIDATE` и `PWA_INIT_MODE` можно переопределить.

Путь нового каталога печатается как `PROFILE_RESULTS`. В нём `normal/` содержит контрольное время, `instrumented/` — измерения со счётчиками, `profile_summary.json` и `.log` — сводку. Считаются вызовы и суммарная длительность `advance`, поиска пересечений, обратного преобразования, SIC и матричной экспоненты, а также количество пересечений, активных SIC и шагов с кэшированным потоком. Времена включают вложенные вызовы и суммируются по потокам; их нельзя складывать, а сумма может превышать wall time. Измерительные часы замедляют выполнение, поэтому ускорения следует брать из `normal/`. Разница сценариев с подключёнными нейронами и без них отражает совместный вклад нейронов, событий и планирования, а не отдельный замер каждого из этих компонентов.
